Backpressure: fast producer, slow consumer

Reactive Streams give the consumer a way to tell the producer to slow down. Without it, a buffer between them just grows until you OOM. Toggle the mode and watch the buffer.

Code: same endpoint, two styles
Spring MVC — blocking
@RestController
public class UserController {

  @Autowired UserRepo repo;
  @Autowired RestTemplate http;

  @GetMapping("/users/{id}")
  public UserDto getUser(@PathVariable Long id) {
    User user = repo.findById(id)         // blocks thread
        .orElseThrow();
    Profile p = http.getForObject(           // blocks thread
        "/profile/" + id, Profile.class);
    return new UserDto(user, p);
  }
}
Threading: 1 servlet thread is held for the full findById + REST call duration. With 200 threads and 100ms latency you cap at ~2000 RPS before threads run out.
Spring WebFlux — reactive
@RestController
public class UserController {

  @Autowired ReactiveUserRepo repo;
  @Autowired WebClient http;

  @GetMapping("/users/{id}")
  public Mono<UserDto> getUser(@PathVariable Long id) {
    return repo.findById(id)              // returns Mono<User>
      .zipWith(http.get()                     // runs in parallel
        .uri("/profile/{id}", id)
        .retrieve()
        .bodyToMono(Profile.class))
      .map(t -> new UserDto(t.getT1(), t.getT2()));
  }
}
Threading: The event loop schedules both calls and is freed immediately. The same 4 threads can have thousands of in-flight requests. Never call blocking code (JDBC, Thread.sleep) from here — it stalls the entire server.

Reference

When to pick Spring MVC
  • Most CRUD apps — simpler mental model, easier debugging
  • CPU-bound workloads — reactive doesn't help when CPU is the bottleneck
  • Heavy use of JDBC / JPA — the JDBC ecosystem is blocking by nature
  • Team unfamiliar with reactive — debugging stack traces across flatMap is hard
  • Low to medium concurrency (under ~2000 RPS) with reasonable latency
When to pick Spring WebFlux
  • High-concurrency I/O-bound services (10k+ concurrent connections)
  • API gateways, BFFs, proxies — making lots of downstream calls
  • Streaming endpoints — Server-Sent Events, WebSockets, large file streaming
  • Slow downstream services where you need to multiplex efficiently
  • You can use R2DBC or have only async data sources
Common pitfalls in WebFlux
  • Blocking the event loop — Thread.sleep, JDBC, blocking RestTemplate all stall the server. Use .publishOn(Schedulers.boundedElastic()) if you must.
  • Forgetting to subscribe — a Mono/Flux is cold; if nothing subscribes, nothing happens. Spring subscribes for you on returned Monos, but inside your code you need to chain.
  • Lost stack traces — operators run on different threads. Use Hooks.onOperatorDebug() in dev or checkpoint() at key points.
  • ThreadLocal doesn't work — request-scoped state must use Reactor Context (contextWrite).
  • Backpressure misuse — onBackpressureBuffer() with no bound just delays the OOM.
Why the thread-per-request model breaks under load

If each request waits 100ms on a database call, one thread serves at most 10 req/s. 200 threads × 10 = 2000 RPS ceiling — and beyond that, requests pile up in the queue and start timing out. The only knobs are: bigger pool (more memory, more context-switching) or faster downstream (not always possible).

WebFlux sidesteps this entirely: the thread is freed during I/O wait, so the same 4 threads can serve tens of thousands of concurrent requests. The new ceiling is downstream capacity or CPU, not threads.

What about Spring 6 / Project Loom virtual threads?

Java 21+ virtual threads (Project Loom) let you keep MVC's simple programming model while getting WebFlux's concurrency. Each request still gets a "thread", but it's a virtual thread — millions are cheap, and JDBC blocking calls are transparently parked instead of holding an OS thread.

For new projects on JDK 21+, this is often the better answer than WebFlux: same code as MVC, similar throughput to WebFlux, no reactive learning curve. WebFlux still wins for streaming and backpressure scenarios.
